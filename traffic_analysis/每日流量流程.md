# 每日流量流程（标准作业 · 2026-10-16 定稿）

> 用户 2026-10-16：「为什么昨天用了这么长时间…你规整一下流量，然后后面都按这个流程来。」
> 从这天起 **只要给到带「流量」的文件（单份 / 一个文件夹 / 下载里一堆散表），默认按本文一路跑到底，不再逐步确认**。
> 详细判据与历史见 [`../WORKFLOW.md`](../WORKFLOW.md) 🅲；脚本清单见 [`../docs/05-脚本清单.md`](../docs/05-脚本清单.md)。

## 0. 一句话

```bash
python -X utf8 traffic_analysis/run_daily.py <文件或文件夹 1> [<文件或文件夹 2> …]
```

**四步**：`[1/4] 入库+生成日报 → [2/4] 自动复核 → [3/4] git commit → [4/4] pull --rebase → push`。
**复核不过就不提交**（exit 1），不会把错数据推上线。
推送成功后还会跑 **`[4/4·b] 线上同步校验`**（比对线上索引末条 + 当日日档/日报字节，只提示不阻断）。

## 1. 触发与文件识别

| 给到的 | 怎么做 |
|--------|--------|
| **一个文件夹**（`10.15日流量\`，里面 6 份表 = 6 个直播间） | 直接把文件夹路径传进去；日期从**文件夹名**识别 |
| **几份散表**（桌面 / 下载，文件名带日期） | 把路径都传进去，脚本**按日期自动分批**（多天一起给也行） |
| **单份表** | 命名成桌面 `流量数据.xlsx`，或直接传路径 |
| **什么都没传** | `run_daily.py` 自动找：桌面 `流量数据.xlsx` → 桌面 `流量数据\` → 桌面/下载里最新的「xx流量」文件夹与散装表（双击 `刷流量数据.bat` 走这条） |

- **认表的判据**：表里有一列 `渠道名称`（或 流量渠道/来源渠道/流量来源/来源），**且同一行表头里还有 ≥3 个指标列**（直播间曝光次数 / 观看次数 / 互动次数 / 新增粉丝数 / 商品曝光次数 / 商品点击次数 / 成交订单数 / 用户支付金额）。**看含义不看字面**（关键词匹配），**表头不一定在第 1 行**（脚本在前 15 行里自己找，常见是第 2 行）。
- **日期推定四级**：`--date` > 所在**文件夹名**（`10.15日流量`）> **文件名**（`小米官方手表10.15日流量.xlsx`）> 表内日期单元格 > 文件修改时间（会打印提示让你复核）。
- **直播间名 = 文件名，但小误差自动矫正**（2026-10-16 起）。**在营名单固定六间**（`daily_update.py` 的 `CANON_ROOMS`）：小米官方手环直播间 / 小米官方手表 / 小米数码旗舰店 / 小米官旗手表直播间 / 小米官方耳机直播间 / 小米智能设备旗舰店直播间。
  - 矫正顺序：已在名单 → 别名表 `ROOM_ALIAS` → 去符号精确匹配 → 去「直播间/直播/店」核名 → 互相包含 → 相似度 ≥ 0.62 且领先次优 ≥ 0.08。多写/少写「直播间」、「直播号」、空格、`副本`、双后缀（`x.xlsx.xlsx`）都能认，并打印 `⚠️ 直播间名已矫正：X → Y（依据）`。
  - **认不出会中止**：在**写盘之前**退出（exit ≠ 0），打印名单 + 两条出路。**绝不会凭空新建幻影直播间**。确实开播了新直播间 → 跟用户确认后加进 `CANON_ROOMS`。
  - 仍可用 `--room "全名"` 显式指定（**不改用户文件**，`source_files` 仍记录真实 basename）；`--room` 里写错名也会被矫正。
- **同一天重复入库 = 覆盖**（打印「⚠️ 同日已有数据，已覆盖」），**且是同字节幂等**：内容一样时重灌后 `git status` 完全干净（连 `generated_at` 都不变），不会产生只有时间戳的空提交。

## 2. 常用命令

| 场景 | 命令 |
|------|------|
| **每天正式跑（推荐）** | `python -X utf8 traffic_analysis/run_daily.py <文件…>` |
| 顺带校验页面（改过页面必跑） | 加 `--page`（多花约 4 秒，跑 `page_check.py`） |
| 先人眼核对、**不提交** | 加 `--no-commit`（只入库+复核） |
| 提交但**不推送** | 加 `--no-push` |
| 文件名认不准 | `--room "小米智能设备旗舰店直播间" <文件…>` |
| 日期认不准 | `--date 2026-10-15 <文件…>` |
| 只重建索引与日报 | `--rebuild-only` |
| 跳过复核（**不推荐**） | `--no-verify` |
| 双击 `刷流量数据.bat` | 等于不带参数跑本脚本（自动找文件）；**换个位置/别人克隆后用也没问题**（见 §9） |
| 不想联网校验线上 | 加 `--no-live`（只关 `[4/4·b]`） |

## 3. 四步各做什么

1. **入库**：`daily_update.py` 解析 xlsx → `data/2026/<date>.json`（主库，含 6 间 totals + channels）+ `data/index.json`（刷新索引）+ `reports/2026/<date>/<口径>.json`（全店 + 每间各一份）。
2. **复核**：`verify_day.py <date>` 六段（见下），**任一段 BAD 就 return 1，不提交**。
3. **提交**：`git add traffic_analysis/data traffic_analysis/reports`（**只加这两个目录**）→ 无变化则跳过 → `git commit -m "feat: 流量数据 <label>日更新"`。
4. **推送**：`git pull --rebase` → `git push` → `git log --oneline -1`。

## 4. 耗时基线（2026-10-16 实测，6 份表 6 个直播间）

| 环节 | 旧做法 | 现在 |
|------|--------|------|
| 解析入库 + 生成日报 | ~10 秒 | **0.4 秒** |
| 数据复核 | 手写脚本 + 三套 playwright，5~10 分钟 | **0.1 秒**（`verify_day.py` 六段） |
| 页面校验 | 同上（`check_traffic_layout` + `_verify_chart_scope` + `audit_traffic_page`，5~10 分钟） | **3.7 秒**快速档 / **12.1 秒**深度档（`page_check.py`，深度档覆盖 **96 个「日期×口径」组合**逐图核数） |
| 端到端（入库+复核，不含推送） | 10 分钟以上 | **0.6 秒** |

## 5. 复核六段（`traffic_analysis/verify_day.py <date>`）

| 段 | 校验内容 |
|----|----------|
| **A** | 源表「整体」行 9 字段（含直播时长）↔ `data/2026/<date>.json` 各间 totals（逐项相等） |
| **B** | 全店 = 各直播间相加（9 字段精确相等，`totals_source` 应为「各直播间相加」） |
| **C** | `reports/2026/<date>/` 7 份日报齐全；每份漏斗首段 == 当日曝光；渠道数与日档一致 |
| **D** | `data/index.json`：天数、升序、末条 == 本次日期、索引 ↔ 日档一致（6 间 / 观看数） |
| **E** | 页面静态契约：`traffic_analysis/index.html` 的 29 个 id 与交互钩子齐全（改名会**静默失效**） |
| **F** | **环比交叉校验**：源表「较上周期」行里平台自己算的 % ↔ 我方前一日存档（6 间 × 8 字段）；**全吻合 = 文件确为该单日数据**，也是解释「异常暴涨/暴跌」的决策性证据 |

> F 段是 2026-10-15「观看 −63.8% 而订单 +540%」那次的产物：先用它证明文件没错，再去查业务原因（大促）。

## 6. 出问题怎么办

| 现象 | 处理 |
|------|------|
| 复核 BAD | **先别提交**。看是哪一段：A/B/D 段多半是源表或日期认错，C/E 段是产物/页面被改名。修完重跑同一条命令 |
| 复核提示「找不到源表（跳过 A/F）」 | 源表已不在桌面/下载（或给的是别的目录）。`run_daily.py` 会**自动把输入文件所在目录传给复核**，所以正常跑不会出现；手工跑 `verify_day.py` 时补 `--src "<目录>"` 即可恢复 A/F 两段（这不算 BAD，不会中止） |
| 提示「不在在营名单里」并中止 | **没写任何数据**（写盘前退出）。先看文件名是不是真新直播间：确属笔误 → 改文件名或用 `--room "全名"`；确是新直播间 → 跟用户确认后加进 `CANON_ROOMS`（必要时补 `ROOM_ALIAS`），再重跑 |
| 想先探名字再入库 | `_artifacts/_probe_names.py <文件>`（exists / guess_room / 是否在 known_rooms / 同日是否已有数据） |
| 线上没同步（`[4/4·b]` 报 ⚠️） | 多为部署延迟或本机网络：Cloudflare Pages 约 8 秒生效，隔几秒再跑一次校验。校验本身**不影响退出码**，也不回滚已提交的数据 |
| 提示「线上 N 字节 ≠ 本地 M 字节」 | 已按 LF 归一后再比（Windows 检出会把 LF 变 CRLF，2026-10-16 修过一次假报）；若归一后仍不等，多半是线上还没部署完，等 10~30 秒再验 |
| 数字看着离谱 | 跑 `python -X utf8 traffic_analysis/verify_day.py <date>` 看 F 段；仍不解就用 `_artifacts/_cmp_days.py <A> <B>`（逐间+全店+渠道 Top3 两日对比）、`_artifacts/_diag_1015.py`（转置打印源表） |
| 线上没更新 | Cloudflare Pages 约 8 秒生效；复检用 `_artifacts/_live_day.py <date>`（**curl 必须加 `-4`**，IPv6 出网会 TLS 超时） |
| push 被拒 | `git stash push && git pull --rebase && git stash pop`（`run_daily.py` 已内置 stash 兜底） |

## 7. 红线

- **只碰 `traffic_analysis/`**（数据 + 页面 + 脚本）：不读也不写 `sales_analysis/`，不动 `主播业绩/业绩demo.html`，**不要用 `run_all.py`**（它只跑订单链路）。
- **不写数据**：只读 `data/index.json`、`data/2026/<date>.json`、`reports/2026/<date>/<口径>.json`；缺口日必须断开（null）；首日不给涨跌色。
- **不改用户原始表**；`git add` **只列本次真正改动的路径**（**禁止 `git add -A`**，工作区常躺别人的半成品）。
- 口径异常渠道判定：`互动÷观看 ≥ 2.5` 且（观看 ≥ 150 或互动 ≥ 50）→ 从互动率合算里剔除并标「口径异常」；`≥ 0.6` 只标「互动率偏高」。
- `traffic_analysis/index.html` 是**手写页**，可直接改；改完必须 `--page` 或 `python traffic_analysis/page_check.py --deep` 过一遍。

## 9. 给别人用 / 换台电脑

1. **拿到仓库**：`git clone` 后任意位置都行（不要改文件夹名/层级，页面路径是硬编码相对路径）。
2. **双击 `traffic_analysis\刷流量数据.bat`** 即可 —— 它会先找同目录的 `run_daily.py`，找不到就去桌面各文件夹里找；没有 `python` 时自动回落 `py -3`。命令行等价：
   ```bash
   python -X utf8 traffic_analysis/run_daily.py <文件或文件夹…>
   ```
3. **文件怎么放**：单份命名 `流量数据.xlsx` 放桌面；或把当天那个文件夹（如 `10.15日流量\`）放桌面；或直接传路径。脚本自己找、自己按日期分批。
4. **提交即同步**：第 3、4 步会 `git commit` + `git pull --rebase` + `git push`，Cloudflare Pages 约 8 秒后线上就是新的；`[4/4·b]` 会用**线上字节比对**告诉你有没有同步成功（网络不通只警告，不回滚）。
5. **前提**：本机有 git 且**已配置该仓库的推送权限**（`git push` 能过）；没有权限时用 `--no-push` 只入库+提交，让有权限的人推。
