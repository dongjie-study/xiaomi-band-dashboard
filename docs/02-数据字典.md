# 02 · 数据字典

> 各数据文件的字段含义。**以本文件为准**——`data_schema.md` 写于 2026-07，已过期（缺了 6 个团队数组等）。

## 一、`sales_analysis/history.json` ⭐ 销售累计主库

**数组**，一天一条，按日期升序。当前 **105 天**（2026-06-01 起）。
只有 `sales_analysis/daily_update.py` 会写它。

| 字段 | 类型 | 说明 |
|------|------|------|
| `date` | str | `YYYY-MM-DD`。⚠️ 可能是 `NaT` —— 见 [06-踩坑#1](06-踩坑与故障.md#1-nat-静默跳过一天) |
| `total_orders` | int | 当天总订单条数（**下单口径，不扣退款**） |
| `total_revenue` | float | 当天总实付金额（元） |
| `avg_price` | float | 客单价 = revenue / orders |
| `products` | dict | 商品短名 → `{orders, revenue, avg_price}` |
| `rooms` | dict | 直播间名 → `{orders, revenue, avg_price, products, type}`；`type` 是团队名 |
| `our_rooms` | list | 我司直播间名（**每天实际出现的**，不是全量名单） |
| `jixie_rooms` / `zongheng_rooms` / `zhumeng_rooms` / `feina_rooms` / `ningyun_rooms` / `lequn_rooms` / `chimu_rooms` / `mile_rooms` / `liangmi_rooms` | list | 各团队当天的直播间名 |
| `comp_rooms` | list | 所有竞对直播间名 |
| `type_summary` | dict | 团队名 → `{orders, revenue, avg_price, rooms}` |

> ⚠️ **`data_schema.md` 已过期**：它只列了 `our_rooms/jixie/zongheng/liangmi/comp_rooms`，
> 实际现在还有 `zhumeng/feina/ningyun/lequn/chimu/mile_rooms` 六个。
> 另外它描述的 `_hourly_stats` 内嵌在 `rooms` 里，**现在已不这样**——小时数据独立成 `hourly/<日期>.json`。

## 三、`sales_analysis/band11_history.json` / `b10pro_history.json`

主打手环对比模块的数据源，`sales_analysis/index.html` fetch。
**数组**，一天一条：`{date, product, product_short, our:{live_o,live_a,card_o,card_a}, lm:{...}}`

- `our` / `lm` = 我司 / 良米
- `live_o` / `live_a` = 直播端单量 / 金额；`card_o` / `card_a` = 商品卡端
- `band11_history.json`：手环11，**9.7 起**，当前 7 条（曾残留 1 条 `date:"NaT"` 的坏数据，2026-09-14 已清除，见 [06-踩坑#2](06-踩坑与故障.md#2-band11_historyjson-里的-nat-残留)）
- `b10pro_history.json`：10 Pro，50 条，已被 9.7 后的手环11 取代展示

## 四、`sales_analysis/daily_summary.json` ⭐ 总结主库

`{schema_version, updated_at, reviews}`，`reviews` 是 **date → 记录** 的 dict。
只有 `band11_review.py add` 会写。**只追加，绝不删历史日期**。

| 字段 | 说明 |
|------|------|
| `date` | `YYYY-MM-DD` |
| `rating` | `好` / `一般` / `差`（人工写的覆盖脚本评级） |
| `written_by` | `claude` / `auto` |
| `written_at` | 写入时间 |
| `good` | ✅ 好在哪——**必须具体到渠道 + 数字 + 对比** |
| `bad` | ⚠️ 差在哪 |
| `watch` | 🎯 盯什么 + **带时间预期**（如「预计 2-3 天见分晓」） |

> 每段 ≤ 90 字（`band11_review.MAX_FIELD`），超了 `add` 拒收。
> **为什么总结要外置成 JSON**：`generate_band11_target.py` 每次都 `Workbook()` 从零重建 xlsx，
> 只写在 Excel 里的内容第二次跑就永久消失。

### 评级逻辑 `band11_review.grade()`

主判据 = **节奏比** = 当日手环11 台数 ÷ 首销月日均需求（60000/31 ≈ 1,935 台）

| 评级 | 条件 |
|------|------|
| 好 | 节奏比 ≥ 1.00 且环比 ≥ -5% |
| 一般 | 节奏比 ≥ 0.75 且环比 ≥ -30% |
| 差 | 其余 |

首销日无环比基准记「好」；**开售次日（9.8）跳过环比判据**。

## 六、`sales_analysis/stats_data.js`

首页概览卡的**预计算快照**，格式 `window.__STATS__ = {...}`，
含 `date / orders / revenue / avg_price / rooms / our_rooms / comp_rooms / team_counts / days`。

## 七、`主播业绩/业绩demo.html` 的 `DAILY_RECORDS`

**业绩主库**，内嵌在 HTML 里的 JS 对象。按日期分块：

```js
DAILY_RECORDS = {
  '2026-09-13': [
    { roomId: 'room_xiaomi_band', shift: 'B', anchor: '张三', sales: 12345.6 },
    ...
  ],
  ...
}
```

- `roomId` 映射见 [`03-直播间与团队.md`](03-直播间与团队.md) 第一节
- `shift`：`A`~`E`（**A1/A2 已合并为 A**，E 不分上下半场）
- **业绩数据只有 2026-08 起**，6/7 月没有是正常的（模块是后加的）
- ⚠️ 这个块在 `archive/update_daily_html.py` 里会被整块改写——虽然 WORKFLOW 已禁用该脚本，改结构时仍要小心
