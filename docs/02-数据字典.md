## 一、`sales_analysis/history.json` ⭐ 销售累计主库

**数组**，一天一条，按日期升序，从 2026-06-01 起（天数随每日入库增长，用 `python band11_review.py status` 看最新日期）。
只有 `sales_analysis/daily_update.py` 会写它。

| 字段 | 类型 | 说明 |
|------|------|------|
| `date` | str | `YYYY-MM-DD`。⚠️ 可能是 `NaT` —— 见 [06-踩坑#1](06-踩坑与故障.md#1-nat-静默跳过一天) |
| `total_orders` | int | 当天总订单条数（**下单口径，不扣退款**） |
| `total_revenue` | float | 当天总实付金额（元） |
| `avg_price` | float | 客单价 = revenue / orders |
| `products` | dict | 商品短名 → `{orders, revenue, avg_price}` |
| `rooms` | dict | 直播间名 → `{orders, revenue, avg_price, products, type}`；`type` 是团队名 |
| `our_rooms` | list | 我司直播间名（**每天实际出现的**，不是全量名单） |
| `jixie_rooms` / `zongheng_rooms` / `zhumeng_rooms` / `feina_rooms` / `ningyun_rooms` / `lepan_rooms` / `chimu_rooms` / `mile_rooms` / `liangmi_rooms` | list | 各团队当天的直播间名 |
| `comp_rooms` | list | 所有竞对直播间名 |
| `type_summary` | dict | 团队名 → `{orders, revenue, avg_price, rooms}` |

## 四、`sales_analysis/daily_summary.json` ⭐ 总结主库

`{schema_version, updated_at, reviews}`，`reviews` 是 **date → 记录** 的 dict。
只有 `band11_review.py add` 会写。**只追加，绝不删历史日期**。

| 字段 | 说明 |
|------|------|
| `date` | `YYYY-MM-DD` |
| `rating` | `好` / `一般` / `差`（人工写的覆盖脚本评级） |
| `written_by` | `claude` / `auto` |
| `written_at` | 写入时间 |
| `good` | ✅ 好在哪——**必须具体到渠道 + 数字 + 对比** |
| `bad` | ⚠️ 差在哪 |
| `watch` | 🎯 盯什么 + **带时间预期**（如「预计 2-3 天见分晓」） |

> 每段 ≤ 90 字（`band11_review.MAX_FIELD`），超了 `add` 拒收。
> **为什么总结要外置成 JSON**：`generate_band11_target.py` 每次都 `Workbook()` 从零重建 xlsx，
> 只写在 Excel 里的内容第二次跑就永久消失。

### 评级逻辑 `band11_review.grade()`

主判据 = **节奏比** = 当日手环11 台数 ÷ 首销月日均需求（60000/31 ≈ 1,935 台）

| 评级 | 条件 |
|------|------|
| 好 | 节奏比 ≥ 1.00 且环比 ≥ -5% |
| 一般 | 节奏比 ≥ 0.75 且环比 ≥ -30% |
| 差 | 其余 |

首销日无环比基准记「好」；**开售次日（9.8）跳过环比判据**。

## 九、`traffic_analysis/` 流量数据（⭐ 流量主库，2026-10-11 起）

**一天一个文件 + 一天一个日报目录**，和销售库（`history.json` 一条数组装全部天）结构不同——因为流量数据**按直播间分开**（一天可能 6 份表 = 6 个直播间），且带 12 个渠道明细，体积大。

层级：`data/YYYY/YYYY-MM-DD.json`（当天全店 + 每个直播间）→ `reports/YYYY/YYYY-MM-DD/<口径>.json`（**全店 + 每间一份**，文件名就是口径名）。

### 9.1 `traffic_analysis/data/index.json`（页面唯一入口索引）

```json
{
  "generated_at": "2026-10-11 20:15:36",
  "start_month": "2026-10",
  "all_scope": "全店",
  "months": [ { "ym": "2026-10", "label": "10月", "count": 8,
                "dates": ["2026-10-10", "2026-10-07", "…"] } ],
  "days":   [ { "date": "2026-10-01", "pretty": "10月1日", "demo": true,
                "rooms": ["小米官方手环直播间", "小米官方手表", "…"],
                "n_rooms": 5,
                "views": 178593.8, "impressions": 3385492.2,
                "paid_orders": 2216.5, "paid_amount": 791637.4,
                "gpm": 4433, "roi": 38.18 } ]
}
```

- `months[].dates` **倒序**（最新在前），页面据此生成月份/日期下拉。
- `days[].rooms` = 当天有数据的直播间列表（**页面「直播间」下拉就用它**，切到没有数据的日期时自动回落 `全店`）；`n_rooms` 是间数；`pretty` 给日期下拉显示（如 `10月1日`）。
- `days[]` 的 `views/impressions/paid_orders/paid_amount/gpm/roi` 都是**全店口径**（各直播间相加），趋势图直接读它，不必逐日拉日文件。
- `demo` 为真的日子页面顶部显示金色「示例数据」提示条。

### 9.2 `traffic_analysis/data/YYYY/YYYY-MM-DD.json`（主库，一天一文件）

顶层 = **全店**口径；`rooms` 里每个直播间一份**结构完全相同**的记录：

```json
{
  "date": "2026-10-10", "demo": false, "updated_at": "…",
  "rooms": { "小米官方手环直播间": {/* 单间记录 */}, "…": {} },
  "…": "顶层是全店的同类记录（totals / ok_totals / metrics / channels）"
}
```

单间记录（顶层全店记录字段一致，只是 `source_file` 是 6 个文件名的拼接）：

| 字段 | 含义 |
|------|------|
| `date` | 日期（页面「数据日期」；缺了会显示成空） |
| `source_file` / `source_sheet` | 源 xlsx 文件名 / 命中的 sheet（sheet 名一般是 `流量趋势`） |
| `channels` | `[{name, 8 个计数字段, evr, ctr, cvr, gpm, share, prev_views, chg, interaction_ratio, anomaly, suspect}]`，**已按观看次数降序**；渠道名原样保留（含 `&` 号） |
| `channel_order` | 渠道名顺序（与 `channels` 一致） |
| `totals` | 该口径合计（8 个计数字段 + `live_duration` / `avg_watch_time` / `qianchuan`） |
| `ok_totals` | **剔除口径异常渠道后**的合计——互动率/涨粉率等「率」类指标用它算 |
| `metrics` | 派生指标（见 9.4） |
| `totals_source` | 合计取自「表内整体行」还是「渠道加总」 |
| `row_sum_mismatch` | 渠道加总与表内「整体」行差 > 0.5 的字段（正常应为空） |
| `anomaly_channels` | 口径异常渠道（互动÷观看 ≥ 2.5 倍，且观看 ≥ 150 或互动 ≥ 50，**已剔除出互动率合算**） |
| `suspect_channels` | 可疑渠道（比率 ≥0.6 但没到 2.5 倍，数据照常参与合算，只在页面标「互动率偏高」） |
| `excluded_interactions` / `excluded_share` | 被剔除的互动数 / 占全部互动数的比例（**>15% 就该找平台核对两列口径**） |
| `skipped_rows` | 跳过的行（`较上周期`、`同行同级优秀值` 等） |

> 8 个计数字段内部名：`impressions` / `views` / `interactions` / `new_followers` /
> `product_impressions` / `product_clicks` / `paid_orders` / `paid_amount`。
> 额外 3 个（**只有「整体」行有**，渠道行是 `—`）：`live_duration`（分钟）、`avg_watch_time`（原始文本如 `58秒`）、`qianchuan`（千川消耗，元）。

### 9.3 `traffic_analysis/reports/YYYY/YYYY-MM-DD/<口径>.json`（日报）

**一天一个目录**，目录里是 `全店.json` + 每个直播间一份（**文件名就是口径名**，页面按 `encodeURIComponent(scope)` 取）。
读的顺序有讲究：先读日文件确认那天有没有这个直播间，再取日报——避免对不存在的口径发请求吃 404。

| 字段 | 含义 |
|------|------|
| `scope` / `room` / `is_all` | 口径名（`全店` 或直播间名）；`room` 与 `scope` 同值（兼容旧读取路径）；`is_all` = 是否全店 |
| `date` / `prev_date` | 数据日期 / 对比基准日期（**页面「数据日期」「对比基准」靠它**） |
| `generated_at` | 状态条右侧的「更新于」，取自前一天文件的 `updated_at`；**内容没变时不会跳时间戳**（重建不会产生空提交） |
| `prev_scope_exists` | 前一日该口径是否有数据（没有就显示「首日 / 无对比」） |
| `totals` / `metrics` / `ok_totals` | 同 9.2 |
| `source_file` / `source_sheet` / `totals_source` | 同 9.2 |
| `anomaly_channels` / `suspect_channels` / `excluded_share` / `row_sum_mismatch` | 同 9.2 |
| `dod` | 逐字段环比：计数字段给 `{prev, chg, dir}`；比率字段给 `{pd_, cd, pp_diff, chg, is_rate:true}`（`pd_`/`cd` 已是百分数） |
| `rules` | 平台规则匹配：`[{key, label, value, value_disp, range, status(ok\|low\|high\|unknown), why, unit, prev}]`；`unknown` 有两种：**没数据**（`value=null`）与**口径不可比**（如互动率 > 100%，有值但今日不判定）——页面分别显示「— 无数据」「— 暂不判定」，后者不计入「达标 N / M」 |
| `channels` | 渠道明细行（含 `anomaly` / `suspect` / `interaction_ratio`，见 9.2） |
| `room_compare` | **全店视角**的各直播间对比行（`name, views, view_share, evr, ctr, cvr, gpm, aov, roi, uv_value, interaction_rate, new_follower_rate, anomaly_channels, suspect_channels, vs_peer_gpm`），按观看降序；页面第 ⑤ 块表格用它 |
| `peer_benchmark` | **同业横向基准**：对 9 个指标各给 `{key, label, unit, nd, median, best:{name,value}, worst:{name,value}, value, ratio}`，来源是「本店各直播间之间的横比」，页面第 ⑤ 块下半用它 |
| `insights` | `{headline[], data[], rules[], actions[]}` 四段文案（结论 / 数据表现 / 规则命中 / 优化建议） |

> `room_compare` 与 `peer_benchmark` **所有口径都会生成**（单间日报里 `room_compare` 是同一批 6 间，方便页面在任何口径下都能显示对比表）。

### 9.4 `metrics` 派生指标（权威口径）

| 字段 | 算法 | 参考区间（`PLATFORM_RULES`，2026-10-11 按真实数据校准） |
|------|------|------|
| `exposure_view_rate` | 观看 / 曝光 | **≥ 3.5%**（平台给量的第一道闸门；真实 6 间 4.53% ~ 9.13%） |
| `view_interaction_rate` | 互动 / 观看 | 只展示不打分（口径不稳定） |
| `interaction_rate` | `ok_totals` 互动 / `ok_totals` 观看 | **≥ 5%**，**剔除异常渠道**后的口径；真实 9.35% ~ 27.59% |
| `product_ctr` | 商品点击 / 商品曝光 | **4% ~ 25%**；真实 3.01% ~ 11.99% |
| `click_cvr` | 成交订单数 / 商品点击次数 | **1.5% ~ 10%**；真实 0.93% ~ 8.46% |
| `gpm` | 支付金额 × 1000 / 观看次数 | **≥ 2000 元**（千次观看成交额；真实 2019 ~ 5938，**不是 200 元**） |
| `new_follower_rate` | 新增粉丝 / 观看 | **0.2% ~ 3%**；真实 0.28% ~ 0.78% |
| `qianchuan_roi` | 支付金额 / 千川消耗 | **≥ 10 倍**；真实 14.03 ~ 46.50 |
| `uv_value` | 支付金额 / 观看次数 | 单个观看带来的成交额（元） |
| `aov` | 支付金额 / 成交订单数 | 客单价（元） |
| `live_duration` / `qianchuan` | 直播时长（分钟）/ 千川消耗（元） | 只有「整体」行有值 |
| `orders_per_hour` / `gmv_per_hour` | 订单数 / 直播小时数；支付金额 / 直播小时数 | 每小时成交单数 / 每小时成交额 |
| `funnel` | 5 段漏斗 | 曝光 → 观看 → 商品曝光 → 点击 → 成交 |

> ⚠️ `PLATFORM_RULES` 里的阈值**单位是百分数**（`3.5` / `4 ~ 25`），不是小数。
> 页面/脚本比较时统一 ×100——写成 `0.035` 会把 5.43% 误判成「偏高」。
>
> ⚠️ 阈值是**按真实数据校准过的**：早期 demo 用的 `gpm ≥ 200`、`点击→成交 5%~40%`、`曝光→观看 8%~30%`
> 比真实分布**差一个数量级**，会让规则表永远全红/全绿。改阈值前先看上面「真实」列的实测区间。
