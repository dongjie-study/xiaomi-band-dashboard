> ```python
> ROOT = Path(__file__).resolve().parent.parent
> sys.path.insert(0, str(ROOT))     # ← 少这一行就会 ModuleNotFoundError
> DATA_DIR = os.path.dirname(os.path.dirname(os.path.abspath(__file__)))
> ```
> 其中 `gen_weekly_report.py`、`generate_august_summary.py`、`generate_september_summary.py`
> **原先没有 `sys.path.insert`**（靠「脚本目录 = `sys.path[0]`」侥幸工作），搬进 `tools/` 时已补上。
> **复制新月份脚本时必须保留这段**，否则报错会指向 `import team_config`，误导排查方向。
>
> 📌 **周报 xlsx 复核（本机没有 LibreOffice，skill 的 `recalc.py` 跑不了；也没有微软 Excel）**：
> `_artifacts/verify_weekly_xlsx.ps1 -Path <xlsx> -Expect <自检.json>` 用 `Excel.Application` COM
> （**本机该 ProgID 实为 WPS 表格 ET**）`CalculateFull()` 重算后校验「零公式错误 + 合计行与自检 JSON 一致
> + 占比列 ∈ (0,1]」。**占比列抽查专门用来抓循环引用**——表格软件对循环引用静默算成 0 且不报错误码，
> `SpecialCells` 抓不到。`.ps1` 必须存成 UTF-8 with BOM，且要用
> `powershell -NoProfile -ExecutionPolicy Bypass -File ...` 跑（未签名脚本被策略拦）。
> ⚠️ WPS 的 ET 是**单实例**且会复用用户正开着的窗口：复核脚本里**绝不能 `Application.Quit()`**
> （会连带关掉用户自己的表格），只能 `Workbook.Close()` 本次这一个；否则文件被 ET 占用，
> 之后 `gen_weekly_report.py` 重跑会 `PermissionError: [Errno 13]`。
> 判断是不是 WPS：`Get-CimInstance Win32_Process -Filter "Name='et.exe'"`——没有 `EXCEL.EXE` 就说明是 WPS。
> 解锁办法：`[Runtime.InteropServices.Marshal]::GetActiveObject('Excel.Application')` 拿到运行中实例，
> 只 `Close()` 目标工作簿（脚本末尾已内置这一步 + 占用自检）。

### 口径要点（改脚本前必看）

- **解析层不能用 openpyxl**：抖音导出的表是 Go Excelize 生成的，**没有 sharedStrings.xml，全是 inline `t="str"`** —— openpyxl 只看得见 1 行 1 列。脚本是**自己解 zip + ElementTree 解析 `xl/worksheets/sheetN.xml`** 的，改解析要沿用这条路。
- 表头**按关键词匹配**，不按字面列名：前 15 行里找「渠道列 + ≥3 个指标列」的那一行做表头；**先精确相等、再退化成包含**（否则「直播时长」会被「直播间曝光次数」抢走）
- 8 个计数字段：直播间曝光次数 / 观看次数 / 互动次数 / 新增粉丝数 / 商品曝光次数 / 商品点击次数 / 成交订单数 / 用户支付金额；另有 3 个只有「整体」行有：直播时长 / 人均观看时长 / 千川消耗
- 行分类：`整体` 行 = 该直播间合计真值（已实测 = 12 个渠道行逐字段相加）；`较上周期` 与 `同行同级优秀值` **跳过**（前者是用户明确要求忽略的）；其余是渠道行
- 一键入口支持**多天混传**：桌面/下载里与「流量」相关的东西会被自动收集（最新的「xx流量」文件夹 + 散装表，文件名带日期如 `小米官方手环直播间10.8日流量.xlsx`），按日期分批入库；提交信息的日期从文件名推（如 `feat: 流量数据 10.8-10.9日更新`，三天以上用「、」连接）
- 派生指标：曝光→观看率 `观看/曝光`、商品点击率 `点击/商品曝光`、点击→成交转化率 `订单/点击`、观看→互动率（**剔除口径异常渠道**）、涨粉率、GPM（千次观看成交额）、UV 价值、客单价、**千川 ROI `支付/千川消耗`**、每小时成交/成交额
- **口径异常渠道改成按数据自动判定**（不再硬编码渠道名）：`互动次数/观看次数 ≥ 2.5` 且（观看 ≥ 150 **或** 互动次数 ≥ 50）→ `anomaly`（剔除出互动率合算，页面标「口径异常」）；`≥ 0.6` → `suspect`（只标「互动率偏高」，照常合算）。真实数据里异常渠道剔除占比 29%~54%，页面会显示这个比例
  - ★ 补「互动次数 ≥ 50」这一档的原因：小渠道常出现「37 观看 / 1010 互动」这种极端错口径，观看数太小不满足 150，旧判据反而放它进互动率合算，把整间互动率抬到 101%；补上这档后整间互动率才回到 15%~32% 的正常量级
  - 互动率 **> 100%** 这种数（两列口径不一致：互动按动作计、观看按人头计）既不算达标也不算不达标：`status='unknown'`，页面标「— 暂不判定」，顶部 pill 显示「N 项暂不判定」，且不计入「达标 N / M」的分子
- 跳过 `同行同级优秀值` / `行业均值` / `合计` / `总计` / `汇总` 行；`1.2万` `3,456` `12.5%` `—` 都能解析
- 日期推定四级：`--date` > **所在文件夹名**（`10.10日流量`）> 文件名 > 表内日期单元格 > 文件修改时间（会提示复核）
- 直播间名认法：按历史入库 + `team_config` 名单精确/包含匹配 → 认不出再正则抽 → 都不行才要求 `--room`
- **平台规则阈值单位是百分数**（`3.5` / `4 ~ 25` 这种），不是小数——写成 `0.035` 会把 5.43% 误判成「偏高」
- 全店口径**每次 rebuild 都从 rooms 现算**（`refresh_all_scope`），不要直接信日文件里存的顶层全店块
