> 日常执行标准看 `WORKFLOW.md`，本文是它的「为什么」和「坏了怎么修」。

## 1. NaT 静默跳过一天

**最危险的一个坑：不报错、不崩溃，只是默默少一天。**

`sales_analysis/daily_update.py:195` 是 `str(df['date'].iloc[0])` —— 取**第一行**的支付时间当整天的日期。
如果源文件**首行是一笔「待支付」订单**（没有支付完成时间），整条记录的 `date` 就变成 `NaT`。
后果链条：

1. `load_daily()` 对它 `strptime` 失败 → **静默跳过这一天**，进度表莫名少一天
2. 同日 upsert 失效 → 重跑会**追加出第二条**
3. 还会污染兄弟文件（见下一条）

**必查**（每次订单入库后、commit 前）：

```bash
python -c "import json;H=json.load(open('sales_analysis/history.json',encoding='utf-8'));print(H[-1]['date'],H[-1]['total_orders'])"
```

打印出 `NaT` → **让用户重新导出**（导出时排除「待支付」），**不要自己猜日期**。

> 📅 实战：2026-09-13 `9.13日订单.xlsx` 首行就是「待支付」，进度表少了一天。

## 2. `band11_history.json` 里的 NaT 残留

> ✅ **2026-09-14 已修复**（见本节末尾）。留档是因为**教训可复用**：修主库时容易漏掉兄弟文件。

9/13 那次 NaT 事故被清理时（WORKFLOW「🚑 修坏数据的标准动作」），修好了 `history.json`，
但**漏了它的兄弟文件** `band11_history.json` —— 失败运行写进去的那条还在，且排在最后：

| # | date | 我司直播 | 良米直播 | 良米卡 |
|---|------|---------|---------|--------|
| 6 | `2026-09-13` | 1899 | 4053 | 610 |
| 7 | **`NaT`** | 1900 | 4056 | 610 |

**为什么它偏偏在最后**：`_save_focus_history()` 里是 `history.sort(key=lambda x: x['date'])`
—— **字符串排序**。`"NaT"` 的 `N`(0x4E) > `"2"`(0x32)，所以坏记录**永远排末尾**。

**危害**（不只是图上多一个点）：`sales_analysis/index.html` 的 `renderB10proModule()` 里有兜底——

```js
var selectedEntry = B10PRO_DATA.find(r => r.date === currentDate);
if (!selectedEntry) selectedEntry = B10PRO_DATA[B10PRO_DATA.length - 1];  // ← 落到最后一条 = NaT
```

**用户选任何一个在 band11 里查不到的日期，主打手环模块就回落到这条 NaT，显示被丢弃的那版数字。**

### 怎么修的（2026-09-14）

1. **先确认该留哪条**——用 `history.json` 的 9.13 数据按 `_extract_focus()` 同样规则重算：
   - 真值：我司直播 1899 / 商品卡 888，良米直播 4052 / 商品卡 610
   - `[6] 2026-09-13`：**我司 1899 / 888 完全吻合**，良米直播差 1 单
   - `[7] NaT`：**我司商品卡 = 0** —— 当天实卖 888 单，不可能是真的 ⇒ 判定为垃圾
   > 那 1 单差额来自 `_extract_focus()` 在**原始 df 阶段**按原始商品名匹配，
   > 而 `history.json` 的商品名经 `product_classifier` 归一，个别配件类订单会算进前者、归到后者别的类目。属可解释差额。
2. 备份 → **带断言**只删 `date == 'NaT'` 那一条（断言：共 8 条、坏记录在 [7]、其余 7 条日期合法、前后邻居正常）→ 落盘
3. 用 `python ui_check.py naTfix` 与 9/14 基线对比：**8 个页面 0 JS 错误，全量差异只有 `sales.rows: 948 → 947`**（正是删掉的那一行）

### 教训（已写进 WORKFLOW 的清理清单）

**修 `history.json` 时必须一并检查兄弟文件**：`band11_history.json`、`b10pro_history.json`、`hourly/`。
坏运行往多个文件写过东西，只清主文件会留下这种「静默显示错数据」的尾巴。

## 4. `直播间服务商汇总.md` 是运行时输入，不是文档

**看着像给人看的 md，其实被代码解析。乱改格式会让工具崩。**

`直播间销量汇总.py:load_service_map()` 读它，格式契约是硬编码的：

| 区块 | 范围 | 解析规则 |
|------|------|---------|
| 一、服务商对照 | `## 一、` ~ `## 二、` | 按 `\n### ` 切块；块头 `### <服务商> — N 个直播间`，**取 `—` 前**、去括号；块内是两列表，**第一列表头必须叫「直播间」**（靠这个跳过表头） |
| 二、商品卡 | `## 二、` ~ `## 三、` | 两列表，表头「渠道标识」，第二列是服务商 |
| 三、忽略 | `## 三、` ~ `## 四、` | 第一列是忽略的直播间名 |

**正因如此，这个文件现在由 `tools/gen_room_docs.py` 自动生成**，不要手改。
生成后脚本会用真正的解析器回读做断言，**解析不过就不落盘**。

> 📅 2026-09-14 发现它已漂移：写着「良米 12 个直播间」，但 `team_config.py` 里良米有 13 个
> ——9/13 加的「小米耳机」没同步。已由生成器修复。

## 13. 一行多商品：`选购商品` 单元格里有 `;`

一个订单行的「选购商品」可能是**多个商品用 `;` 拼接**，例如：

```
【新品上市】小米手环10Pro…陶瓷白-(73679);【自营国补】小米手环11…NFC版 粉金-(81236);【自营】…NFC版 黑色-(81251)
```

**两套统计对它处理不同**：

| 统计 | 做法 | 这一行算谁的 |
|------|------|------------|
| `_extract_focus()`（band11 / 10Pro 对比） | 在**整串**上跑正则 | 算 **1 单手环11** |
| `history.json` 的**房间级**归集 | 按 `;` **拆开**分派到各商品 | 可能归到 **10Pro** |

所以同一天的手环11 数字，两处会差 1 单。
📅 2026-09-13 实测：`band11_history` 良米直播 **4053**，拿 `history.json` 倒推是 4052，差额正是这一行。

> ✅ **以 `band11_history.json` 为准**——它由原始文件直接算出，与源文件**逐位一致**（已用原始 Excel 复核）。
> ⚠️ **别拿 `history.json` 倒推来复核 band11 数字**，倒推是近似值。

## 14. 悬浮小管家：三个最容易踩的坑

> 完整维护手册见 `交接说明.md` 第十二节；页面侧规则见 `04-页面与模块.md` §六。

### ① 脚本生成页重跑后，悬浮球消失

页面生成器（月度总结四页 / 耳机专报 / 618）是**整份重写 HTML**，
注入进去的那行 `<script src="assistant-widget.js?v=N">` 会被一起冲掉。

**修法**：

```bash
python tools/inject_widget.py --check    # 看哪些页面掉了
python tools/inject_widget.py            # 补回来（幂等，重复跑不会插重复）
```

> 不用改生成器脚本 —— 补跑一次注入就行。

### ② 改了组件却"线上没变化"

页面引用带版本号 `assistant-widget.js?v=N`，**`N` 不变时浏览器直接用缓存**。

`assistant-widget.js` 顶部的 `VERSION` 和 `tools/inject_widget.py` 里的 `VERSION`
**必须一起 +1**，再跑注入、再 push。漏了这一步，同事刷新多少次都是旧版。

### ③ 出现"两个球"

`workbench.html` 是用 iframe 装模块页的，子页面里如果也渲染组件，就会出现外层一个、内层一个。
组件开头那句

```js
try { if (window.self !== window.top) return; } catch (e) { return; }
```

就是防这个的，**不能删**。

## 15. 「接口测通了」≠「页面能跑」（教训，2026-09-26）

数据小管家上线初期，用户反复反馈「点进入没反应」「问问题发不出去」。
排查过程一路修了：

1. `.gate{display:flex}` 覆盖了 `hidden` 属性 → 加 `.gate[hidden]{display:none!important}`
2. `API_BASE` 写成带 `/api` 后缀，拼出 `/api/api/chat`
3. **真正的根因**：`chipsInit()` 里 `send(s)}};` 多了一个右括号 —— **整个页面脚本语法错误，
   自第一版起从未执行过**。而当时所有测试都只打接口（`curl /api/chat` 一直通），
   所以完全没暴露。

**结论：前端必须让脚本本身真跑一遍。**

现在有 3 个 DOM 桩端到端测试（`assistant-server/test-*.cjs`），
用 `vm.createContext` + 手写迷你 DOM 把页面/组件脚本在 Node 里执行，再打**真实后端**对账：

| 测试 | 覆盖 | 什么时候必须跑 |
|------|------|--------------|
| `test-widget.cjs` | 悬浮组件 30 项（含 iframe 跳过、口径、真实问答） | 改完 `assistant-widget.js` |
| `test-page.cjs` | 模块页 10 项 | 改完 `数据小管家/index.html` |
| `test-accuracy.cjs` | 6 个真实问题的答案准确性 | 改完提示词 / 工具 |

> 桩的两个易漏点：`childNodes`（不提供会在 `xx.childNodes.length` 直接抛错）、
> `document.createElement('div')` 的**首次调用要返回预设的宿主元素**（脚本把它当 shadow host）。
> 另外口令校验走的是真实 `/api/chat`，要**轮询等待**（5~30 秒），不能 `sleep(600)` 就断言。

## 16. 批处理里写中文 = 逐行串码（2026-10-11 实测）

给流量链路做「一键入口」时，`刷流量数据.bat` 里既有中文提示又有中文路径，
结果 cmd 报出一堆莫名其妙的错：

```
'p' is not recognized as an internal or external command
'le' is not recognized ...
'ROFILE*' is not recognized ...
```

看着像**每行开头被吃掉 2~3 个字节**。踩了三个坑叠在一起：

1. **中文内容 + cmd 解析**：cmd 是按**当前代码页逐字节**读 .bat 的，文件是 UTF-8
   而控制台是 GBK（936），`chcp 65001` 只影响输出、不影响已经开始的**按字节重读**，
   于是长行被截断/错位；行里带全角括号时更乱。
2. **行尾必须是 CRLF**：LF-only 的 .bat 同样会错位。
3. **中文路径经过 `cmd /c` 传参**：`%USERPROFILE%\Desktop\小米手环…` 会被降级成 `???`
   （`python: can't open file '...\???????'`）。

**修法（已落地）**：

- `.bat` **保持纯 ASCII**，只做一件事：`python -X utf8 "<绝对路径>\traffic_analysis\run_daily.py" %*`
  ——路径里根本不出现中文（用 `%USERPROFILE%` 拼不出来时就让 Python 自己按 `__file__` 定位工程根）。
- 所有中文提示放到 **Python** 里（`sys.stdout.reconfigure(encoding='utf-8')`）。
- 文件用 **CRLF** 写盘（本仓库里 `traffic_analysis/刷流量数据.bat` 就是这样）。
- 一句话原则：**批处理负责「调用」，不负责「说话」。**

## 17. 页面百分比末位「差 0.01」= 浮点 toFixed，不是数据错（2026-10-29 实测）

深度档校验报「2026-10-29 小米数码旗舰店 转化率末点 涨粉率 页面 0.48 != 期望 0.49」，
但日报里 `metrics.new_follower_rate` 就是 `0.00485`（=0.485%），另一天同一现象反向出现过
（`0.00275` 应显示 0.28，页面给 0.27）。

根因：`0.00485 * 100` 的 double 实际是 `0.48499999999999999…`，
JS 的 `toFixed(2)` 按**二进制实际值**截断 → `0.48`；
而校验脚本用 `Decimal(repr(v)).quantize(..., ROUND_HALF_UP)`，走的是**十进制字符串**语义 → `0.49`。
0.485% 的正确两位小数是 0.49%，所以是页面错、校验对。

**修法**（`traffic_analysis/index.html` 的 `fixedNum(x, n)`）：先把数值转成「最短往返十进制串」，
再用 `Number(mant + 'e' + (exp + n))` 十进制移位、`Math.floor(x + 0.5)` 半进位。
**不要**用 `Math.round((v + 1e-9) * 100) / 100`：那会把真正的 0.2749…999 也顶上去，
实测 194 组合里会从「1 处不一致」变成「2 处不一致」（`0.00275` 被多进位）。

- 全量等价性测试：970 个「日报 metrics 比率 + 渠道 evr/ctr/cvr/interaction_ratio」用例，
  旧写法错 1 个、`fixedNum` 错 0 个。
- 改用 `fixedNum` 的地方：`rateCard()` 值/前一日、`seriesOf(isRate)`（趋势图比率线）、
  `RATE_METRICS` 的 `all(r)`（渠道走势「该口径整体」那条虚线）。
- 教训：**页面显示的舍入口径要和校验脚本一致**，而校验脚本的参照必须是十进制语义；
  别用「加 epsilon」这类土办法绕过，先确认源值到底是 0.485 还是 0.4849999。

## 18. 新月份入库了、侧边栏却没有那个月的标签（2026-11-01 → 11-02 实测）

现象：11-01 六份流量表入库、复核、推送、线上索引 32 天且 `months` 里确实有 `2026-11`，
流量页顶栏月份下拉也有「11月（1 天）」，**但工作台左侧「流量分析」下面只有「十月」**，用户看不到 11 月。

根因：左侧「月份→日期」二级菜单的**月份条目是写死在 `modules.json` 的 `subModules`（`monthKey`）里的静态配置**。
数据里多出一个月、`index.json` 的 `months[]` 变了，都不能自动变出新条目 —— 只有「日期列表」是动态 fetch 的。
销售分析同一个毛病（当时缺九月、缺十一月）。

**修法（已落地，2026-11-02 提交 `f15bcce` + `hydrateSalesMonths`）**：
`workbench.html` 在 `renderSidebar()` 之后调
`hydrateDynamicMonths()`（流量：`data/index.json` 的 `months[]`）与
`hydrateSalesMonths()`（销售：`window.__STATS__.dates` 按月聚合），
用 `renderDynamicMonthItems()` **重建**月份条目（中文月份名 + 「（N天）」+ 最新月 NEW）。
`modules.json` 里的 `monthKey` 条目退化为**首屏兜底**，漏加也不影响显示。

**教训**：
1. 「数据有」≠「界面有」——凡是**导航/枚举类**的 UI，要问一句「这是数据驱动的还是配置写死的」。
2. 跨月/新维度上线后，验收要**点名看那个新枚举**（这里就是「11 月的标签」），只看数据 JSON 和页面顶栏会漏掉侧边栏。
3. 已经自动化的事要写进 `CLAUDE.md` / `WORKFLOW.md`，否则下个月换个人（或换一天的我）又会去手改配置。

## 19. 「终端构成」6 份文件内容完全一样 → 是账号级口径，不能相加（2026-11-05 实测）

现象：用户按直播间给了 6 份 `xx流量-终端构成.xlsx`，脚本按文件名逐间入库、再做「全店 = 各间相加」，
结果 11-01 支付变成 **9,924,478.74**，是真实值的 **6 倍**。

根因：平台这份「流量-终端构成」是**账号级（全店）**导出，**不按直播间切分**。
6 份文件除了 xlsx 元数据（时间戳）不同，63 行 × 37 列数据**逐格相同**（MD5 不同、字节数差 ±30，容易误判成「6 个不同报表」）。

**修法**：入库时对每天数据做**内容指纹**（终端×售卖类型×26 指标的排序 JSON）分组，
- 只有 1 个指纹、且来自多个文件 → `scope_mode='account'`，落成单一「店铺整体」口径，并记 `duplicate_files`
- 出现多个指纹（真的逐间导出）→ `scope_mode='rooms'`，逐间落盘并在有 2 间以上时补「合计」（加总 + 比率重算）

**教训**：① 同名多份 ≠ 多份数据，先比内容再相加；② 「文件数」不是「口径数」，报数前必须拿源表某一格（如「整体/全部」支付）对一次量级；
③ 终端构成含直播 + 短视频 + 商品卡全部成交，与「流量分析」的直播间口径**不可相加或对比**（11-01：292.4万 vs 195.3万）。

**2026-11-05 追加（真按直播间只认截图）**：平台页面**按直播间筛选后**的数字与账号级导出不同，但 **xlsx 导出无论选哪间都吐同一份账号级数据**（复测 6 份 md5 全等 `a31a68061f35`）。因此按直播间取数的唯一可靠路径是**在页面上筛好直播间再截图**：
`shots/<日期>.json`（人工转写 7 个数字列：终端/商品曝光/商品点击/曝光→点击率/点击→成交率/曝光→成交率/千次曝光支付）→ `ingest_shots.py` 入库（`scope_mode='rooms'`）。
截图被截断（行没截全）时，用「整体 − 已见终端」的**差额行**补 曝光/点击/曝光→点击率，其余留空（页面显示 —），**绝不猜数字**；差额为负说明转写错，脚本直接报错。`daily_update.py`（xlsx 链路）自此停用。

**2026-11-06 追加（两个新坑）**：
① **售卖类型可能是「合作」**：平台下拉框写的是「售卖类型 / 直播间」，同一批截图里 5 间是「自营」、小米官旗手表直播间是「合作」。若页面/入库按全局「自营」取，官旗手表整间会取不到数据显示空。修法：`shots` 支持单间覆盖 `{sell:'合作', terminals:{…}}`，日档 `scopes[<间>]['sell_types']` 各存各的，页面 `sellTypes(day)` 改为按当前口径取，`setScope()` 里同步纠正 `CH.lineSell`。跨日口径不同（11-01 官旗手表=自营、11-02=合作）时**不做环比**，KPI 写「前一日『自营』口径 · 无同口径对比」，避免拿自营跟合作比。
② **截断的间「整体支付」与「可见终端相加」不闭合**：11-02 官旗手表 整体推算 24,639.81 vs 可见终端相加 24,739.43（差 −99.62 元 = −0.40%），因为看不到的行也带支付、且平台「千次曝光支付」是各行四舍五入值。`verify_day.py` 的 [B] 段对**含差额行的间**放宽到 2% 并打印 ℹ️，没截断的间仍用精确容差（0.005 元/千次曝光）。
③ 顺带修掉一个隐藏 bug：`INDEX.days` 是**倒序**（最新在前），`showDay()` 原来写 `PREVDAY = days[i-1]` 取到的是「后一天」，导致最新一天显示「无对比基准（首日）」、旧的一天反而拿未来做基准。改成 `days[i+1]`。

**2026-11-07 追加（平台侧口径微差，不是转写错）**：11-03 小米数码旗舰店「整体」曝光 372,446，而可见 6 个终端相加是 372,466（**多 20**）；11-04 小米官方耳机直播间「整体」点击 3,966，6 个终端相加 3,968（**多 2**）。截图逐格复核无误 → 是平台「整体」与逐终端列表之间的去重/四舍五入差，量级 0.005%~0.05%。
处理：ingest_shots.py 新增 MICRO_IMP=100 / MICRO_CLK=20 两个容差 —— 只有当「整体 − Σ终端」为**负**且曝光差 ≤100、点击差 ≤20 时才不报错，记进日档 micro_diff，**保留平台「整体」值、不补差额行、不猜数**；超出这个量级仍然直接 SystemExit（真转写错会被拦住）。verify_day.py 的 [B] 段同步按 micro_diff 放宽曝光/点击/推算支付容差并打印 ℹ️。

**顺带一条**：源表的「退款率（支付时间）」**不是**「退款订单数 ÷ 成交订单数」。实测 11-01 退款订单数 7,585 / 成交订单数 13,729 = 55.2%，而源表退款率写 27.44%。
所以这两个比率**不做重算**：单口径直接取源表值，跨口径合计时置空（页面显示 —）。

**2026-11-08 / 11-09（模块下线又恢复）**：11-08 用户看占比图出现 >100% 判定「数据都是错的」，要求整个模块下线（commit `c7f3efa`，19 files / −6044 行，含 `git rm -r terminal_analysis`）。
11-09 用户又说「恢复呀」→ 从 `c7f3efa^` 还原 13 个文件 + 重新接回 `modules.json` / `workbench.html` 两个 SOURCE map，并修掉第 21 条的占比 bug、补 11-05 数据后重新上线。
教训：**下线 = 删代码，但历史还在 git 里**，恢复时按 `c7f3efa^` 抠文件比手抄快；恢复后必须把「为什么被下线」那个 bug 一起修好，否则上线即复发。

## 20. 页面被工作台 iframe 嵌入时点「返回工作台」→ 导航栏重复（2026-11-05 实测）

现象：在「终端流量分析」页面点左上角「← 返回工作台」，画面里出现**两层侧边栏 / 两套顶栏** —— 工作台被塞进了工作台的 iframe 里。

根因：该页是 `workbench.html` 用 `<iframe id="iframePanel">` 打开的；`返回工作台` 写的是普通 `<a href="../workbench.html">`，
点击后**在 iframe 内部**跳转到工作台，于是出现「工作台套工作台」。其它页面（销售分析/流量分析）的同类链接都带 `style="display:none"` +
`if(window.top===window.self)` 才显示，所以从没暴露过这个问题。

修法（`terminal_analysis/index.html`）：
```html
<a class="back-home" id="backHome" href="../workbench.html" target="_top" style="display:none;">← 返回工作台</a>
<script>
if (window.top === window.self) {
  var _back = document.getElementById('backHome');
  if (_back) _back.style.display = 'inline-flex';
}
</script>
```
双保险：① iframe 里**根本不显示**这个链接（顶栏已有工作台导航）；② 即使显示，`target="_top"` 也只跳顶层窗口，不会再套一层。

**教训**：给「被 iframe 嵌入的模块页」加任何指向外层页面的链接/跳转，先问一句「它在 iframe 里点会怎样」；
要么 `target="_top"`，要么 `window.top === window.self` 才显示。验收必须在**工作台里点开模块**的状态下做，单开页面测不出来。

## 21. 「占比 / 100% 堆叠」只能用于可加指标 —— 比率型指标画占比必然出 >100%（2026-11-08 实测）

现象：终端流量分析页「终端占比逐日趋势」指标切到「曝光→点击率」，占比出现 **97.39% / 114.11% / 106.75% / 123.31%**，
用户判定「数据都是错的」，直接要求把整个模块下线。

根因：`renderShare()` 拿每个终端的值除以「整体」行同一指标。这个算法只对**可加指标**（金额、次数、件数）成立；
比率型指标（曝光→点击率、点击→成交率、千次曝光支付、件单价、退款率）的「整体」是**重算出来的比率**，不是各终端相加，除出来必然失真。

修法（2026-11-09 恢复模块时一并修）：
- `terminal_analysis/index.html` 新增 `isAdditive(key)`（`METRICS` 里 `kind` 为 `money`/`int` 的才可加）与 `additiveKeys()`；
- 饼图 / 占比堆叠 / 售卖类型构成三处 chip 只用可加指标（`renderChips()` 里纠正 `CH.pie`/`CH.share`/`CH.sell`），`renderPie()`/`renderShare()`/`renderSellPie()` 入口再兜一次；
- `renderShare()` 的分母从「整体」行改成**各终端相加**，保证每列加起来 100%；
- 新增 `#tmPieNote` / `#tmShareNote`：「占比只对可加指标有意义，比率/平均值不出占比」。

**教训**：① 画「占比」前先问「这个指标相加有意义吗」——只有**可加量**能出占比，比率/均值/单价这类**派生量**永远画原值。
② **指标 chip 和图表类型要绑定**：一组 chip 里混着可加与不可加指标时，图表不该跟着切，而应禁用或换算法。
③ 用户说「数据都是错的」时先怀疑自己选的**算法/口径**，别急着辩解数据源 —— 和第 19 条（同名多份 ≠ 多份数据）同类：**能算出漂亮数字 ≠ 算法成立**。
